# 源文件消失时归档而非删除历史记录

大多数被统计的 CLI 工具会自行清理本地日志：Claude Code 默认只保留 30 天（`cleanupPeriodDays`），Codex、Gemini 等也各有轮转策略。ADR 0003 里“按本轮实际看到的路径清理已消失文件”的对账语义，原意是清理用户主动删除会话后的残留记录，但同一套逻辑也会把这些工具自己清理掉的日志一并从统计里抹掉。

后果是：sqlite 缓存本应比原始工具的本机日志活得更久——这是本工具相对于每次现场扫描、不落库的同类 CLI（如 ccusage）最大的差异化能力——但对账逻辑把这个优势直接抵消了。用户在界面上选择“全部历史”，实际看到的只是“各工具还没来得及清理掉的那部分历史”，且清理时机不可预期、没有任何提示,数字会在某次自动摄取后无声变小。

## 决定

`usage_records` 新增可空的 `archived_at` 列。摄取对账阶段发现某个已缓存路径在本轮扫描中不再出现时，不再物理删除该路径下的记录，而是把它们的 `archived_at` 置为当前时间（幂等，只处理尚未归档的行）；同时清理 `ingested_files` 里对应的缓存指纹，因为文件已不存在，没有 mtime/大小可供下次比较。

已归档记录在所有聚合查询（总览、趋势、按维度拆分、会话列表等）中与未归档记录一视同仁地计入统计——它们代表的用量真实发生过，只是原始文件不再存在。设置页的来源健康表新增“已归档”列，让用户知道这部分数字的来源；新增的 `purge_archived_records` 命令允许用户按来源或全量显式永久删除已归档记录，作为唯一的物理删除入口。

若某个路径重新出现（比如从备份恢复），照常按“文件内容变化”处理：整段解析、替换该路径下的记录，不区分之前是否被归档过。

## Consequences

- 摄取报告新增 `records_archived` 字段，与真正的物理删除 `records_removed`（目前只用于清理未知 Source 的记录）区分开，避免把两种语义混在一个数字里。
- sqlite 缓存体积只增不减，除非用户显式清理归档记录；这是有意为之的取舍，用换取“历史不因工具轮转而消失”的正确性。
- `SourceDiagnostic.record_count` / `total_tokens` 口径不变（含归档），新增 `archived_record_count` 专门标注其中有多少已经脱离了活跃文件。
- 归档只发生在“摄取时看不到之前见过的路径”这一条路径上；被判定为解析失败的文件（`files_failed > 0`）仍然沿用 ADR 0003 的“保留上次正确缓存”语义，本轮不做归档对账。
- 不引入自动过期/自动清理归档数据的策略；是否清理、何时清理完全由用户决定。
